# 阶段 2：受控规则骨架补充设计

状态：用户于 2026-10-11 回复“采用 A，认可草案（推荐）”，方案 A 已批准，详细计划已确认并开始实施；真实验收尚未通过。原[专题设计](stage-2-custom-stories.md)与[实施计划](stage-2-implementation-plan.md)仍为基础约束；本补充覆盖新故事生成方式。详细[实施计划](../superpowers/plans/2026-10-11-controlled-story.md)已于 2026-10-11 确认，沿用已选的当前会话顺序实施方式。不能把设计批准作为功能验收。

## 目标与实测依据

目标仍是三角色（主角与两位 NPC）、五地点、三个不同后果结局，古代/近现代/未来真实创建并完成九条结局路径，保留无密钥 Demo、旧存档、固定真相、失败无半节点、费用与 Trace 审计。完整新前端和图片仍在阶段 3。

截至 prompt 4 有效轮次，固定清单结果为 1/12，15 次实际调用，188.375 秒；新增用量 input 60,862/output 27,443，保守估算 0.383927 CNY，全库预算 1.248071 CNY。没有新未知费用；该金额包含历史保守估算与用户核账，不能称为全部实际账单。历史报告和未通过案例全部保留，详情见[实测报告](../evaluation/2026-10-11-stage-2-supplement-results.md)。

已核对的失败：古代初稿同一行动两规则同时满足，修复后信任溢出；未来两稿同一个结局不可达。近现代创建通过，但三个路径分别出现不存在的发言 ID、同一 NPC 两条对白、主角对白。叙事输入约束的修复在原范围内另行验证；它不能解决规则图的生成可靠性。

## 两种方案

| 方案 | 优点 | 代价与限制 |
|---|---|---|
| A：服务器固定已验证规则骨架，模型填写故事内容（推荐） | ID、触发条件、效果与三结局路径由确定性构造保障；继续普通单模型流水线 | 首版新故事共享调查结构，减少规则与路线自由度；内容质量仍可能被语义检查否决 |
| B：继续自由生成完整 Story，改为分步生成或更强推理配置 | 保留更自由的规则与路线 | 新增调用、预算和时延；仍不能保证修复成功，需要新实测，不继续仅靠扩写提示试错 |

推荐 A，因为当前阶段需要首先交付可运行的自定义故事。故事的题材、人物、真相、证据表述和结局后果仍由模型生成；服务器提供可执行结构。没有将模板包装成多 Agent，也不预设模型质量或时延必然通过。

## A 的具体边界

1. 新增一份版本化规则骨架，固定三角色槽位、五地点槽位、证据/披露/承诺/事件槽位和三结局见证。骨架必须用现有状态更新入口完成穷举验证，所有地点、证据与结局可达，无规则冲突或信任溢出。15–25 行动仍为体验目标，报告实际路径长度。
2. 每个新故事生成独立实体 ID，填入骨架引用；不使用 Demo 固定 ID。模型只返回严格内容协议：人物姓名/目标/外貌、地点/对象的公开描述、对应槽位的证据及事实、秘密、反馈与结局后果。槽位名称与数量受控，拒绝额外字段；模型不能返回或覆盖可执行条件、效果、状态和出口。
3. 普通内部组装函数把内容与骨架合成现有完整 Story；不调用 provider、不写数据库、不执行模型代码。固定事实与证据关联以及角色知识的槽位关系必须在骨架中清楚定义，让模型知道各段内容应支持什么关系。若事实、反馈或结局与该关系矛盾，语义检查仍可否决。
4. 新生成/内容修复操作采用独立版本和严格 Pydantic 输入输出协议，通过既有执行边界调用供应商。Trace 保存骨架版本与生成来源，不保存密钥、会话凭据或隐式推理。仍只允许一次修复；修复只改内容，不能改规则图。120 秒单次、300 秒创建总限时以及既有费用保护保持。
5. 组装后仍完整运行 Story 引用检查、有界可达性、语义检查和公开信息检查，再等待显式确认；不跳过检查或在失败时伪造成功。批准后沿现有路径冻结版本和根节点，普通调查回合、分支、回放和恢复机制不改。
6. 既有已保存节点与故事版本保持原样；旧失败报告不替换，不重新解释为成功。不覆盖已批准近现代故事。新默认仍是普通单模型模式，OpenAI/图片/多 Agent 保持未开放。

## 验证与实施顺序

方案 A 已批准，详细实施计划已编写，已确认，沿用当前隔离工作树和当前会话顺序实施。范围只包含以下任务：

1. 冻结骨架与内容协议，测试缺失/重复槽位、额外规则、角色/年代不符、身份不符；证明三个结局见证及全部规则状态合法，记录搜索数量。
2. 实现纯组装函数与新操作版本，以 RED→GREEN 验证 ID 映射、事实关系及严格边界；集成现有创建和一次修复流程，故障不提交候选或节点。
3. 完整后端、固定故障清单、规则/旧存档兼容、迁移一致性检查；记录模拟与确定性结果，核对原样回放和批准故事哈希。
4. 重新用原 12 项真实清单在同一真实测试库执行。报告必须注明骨架/内容协议/prompt/模型/价格版本、尝试、用量、估算与实际账单来源、时延、失败与恢复记录；保留历次失败分母。
5. 至少一位真实评审阅读三故事真相证据与保存的完整路径，核查证据支持、公开泄漏、事实冲突及结局差异。自动通过不能代替人工核查。全部门槛通过后才更新阶段状态和验收提交。

主要风险是模板的剧情自由度与内容映射质量；如用户不接受固定结构，选择 B 并先明确调用/时延边界。两种方案都不允许减少结局、放宽校验或靠多次抽样只留下成功故事来宣称原清单通过。

## 实施细化与来源

初版骨架沿用已批准《雾港》样本的调查拓扑，生产资源单独冻结，不从测试目录加载，原样本不修改。2026-10-11 只读验证原样本：70 个状态，三结局最短见证各 21 行动。抽象关系为六类事实：风险指令、保护性偏转、主动破坏措施、救援经过、双方隐瞒、受保护者。对应角色知识、证据关联、披露、承诺与结局条件固定；模型依所选年代重新构造内容，不能改变这些关系。该事实关系也属于首版共享结构的限制，详细计划提供协议、组装和版本边界；骨架、协议与创建集成已通过自动验证，真实故事质量和人工验收仍未通过。
