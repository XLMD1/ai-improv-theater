## 已批准 R1 的具体实施边界

1. 为新创建任务固定新的创建/呈现协议版本，在确认前保存并校验，批准后保持；旧任务无新标记走原流水线。不得按实体 ID 前缀猜测模式，不改变本轮已批准的三个故事或其他旧故事的呈现方式。具体持久化路径须在实施计划中写清；必要时增量迁移，不原地改旧数据。
2. 呈现函数只消费现有服务器裁决产生的反馈和通过玩家公开投影的内容，不查询隐藏真相来写场景，不向模型提供秘密。不得将完整 rules、truth 或 undiscovered evidence 拼入玩家响应。普通内部纯函数不为了包装而注册工具。
3. 不在生成失败后回退成 R1；R1 是新故事从创建起就固定的明确模式。非法/重复行动沿用既有裁决，不移动、不发线索。没有证据的行为不能靠呈现文本补齐。
4. 通过现有状态更新、提交与不可变 Node 路径保存场景；不直接写世界状态。回放只取保存内容，恢复保留原输入与父节点，兄弟分支不串历史。将呈现协议写入内部 Trace 和评测来源，不能假造未发生的 provider attempt 或 token。
5. 不跳过创建阶段的 Story/schema、可达性及故事语义检查。反馈内容仍属创建时审核的故事内容；人工须核查其中是否在触发时合法披露、支持真相，以及结局后果是否相符。直接呈现只能消除新增扩写，不能保证故事原文永远正确。
6. 原固定 12 项、三背景、三结局、自由文本路径不减少；报表区分真实故事/行动理解与确定性呈现，原失败保留。实际模型、调用次数、用量与时延分别记录。通过所有机器与真实人工门槛后才能标记阶段完成。
7. 阶段 2 设计的“每轮生成再语义否决”要求必须明确修订为上述新故事呈现模式；不能默默绕过原验收要求。前端、图片、包装、OpenAI 与多 Agent 不纳入本补充。
