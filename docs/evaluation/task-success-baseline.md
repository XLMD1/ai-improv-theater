## 1. 目录职责与入口

`evals/` 放可执行评测入口及案例清单，`backend/tests/` 放断言和固定故事 fixture，`docs/evaluation/` 放口径、运行说明和已执行报告；运行原始结果进入 Git 忽略目录。不另建 `benchmark/`，不用同一份故事 JSON 的多份拷贝制造漂移。

阶段 1 的最小入口为 `evals/run_stage1.py`，案例清单为 `evals/cases/stage1.json`，统一读取 `backend/tests/fixtures/mist_harbor_investigation.json` 及其版本/hash；这些路径已实现。fixture 在用户审定前为 draft，机器评测可以用于开发，但不能代替批准。纯规则评测不需要模型密钥或用户数据库；旧存档集成回放必须使用独立 `_test` PostgreSQL 库。

已验证调用方式：从根目录使用安装了 backend 测试依赖的 Python 执行 `python evals/run_stage1.py --suite rules`；`--suite legacy --database-url-env MIGRATION_DATABASE_URL` 单独运行旧存档兼容集成案例，先校验数据库名以 `_test` 结尾，错误配置拒绝连接及迁移。首次运行 legacy 前须已对该独立测试库执行迁移；本脚本不迁移或重置用户故事库。报告写入 runtime/evals/<run_id>/report.json，失败明细使用稳定代码，pytest 子进程只通过状态钩子保存安全计数 JSON，不保存原始诊断、node ID 或捕获输出；清除继承的 PYTEST_ADDOPTS 并覆盖 addopts，发现 deselected 就计错误。

## 2. 成功的定义

每个 case 固定 ID、suite、故事/引擎版本、fixture hash、初始快照、行动序列或故障注入、预期裁决/终态及不变量。规则预期由人工审定样本与明确规则确定，不能临时让被测模型给自己评分。一个 case 只有全部断言成立才成功；拒绝非法行动是该负例任务的正确成功结果，不等于玩家达成结局。

`task_success_rate = successful_cases / total_cases`。`total_cases` 在运行前由选定清单冻结；skipped、error、未实现和超时都不算成功，不能从分母静默移除。总数为零返回空套件错误，不能报告 100%。报告单列 succeeded、failed、error、skipped 及每个失败 ID/原因；非全部成功或必需套件未执行时返回非零退出码。

分开报告 `rules`、`legacy`、`runtime_simulated`、`real_model`，不可合并成一个宣称 AI 能力的数字。规则套件证明确定性正确性；模拟故障套件证明处理行为；真实模型套件才度量真实端到端任务。结构合法率、fallback 率和安全失败率与任务成功率分别列出，安全失败不算真实玩家任务完成。固定样本全部通过是验收门槛，不能从小样本推断所有故事都成功。

## 3. 阶段 1 必需案例

| 套件 | 最少覆盖的独立任务 | 全部断言要求 |
|---|---|---|
| rules | 三个结局各一条完整路径 | 条件成立、后果不同、证据和事件按规则产生 |
| rules | 同地点连续调查/交流 | 地点不隐式改变，状态符合规则 |
| rules | 重复调查、未发现证据出示、错误地点目标 | 明确拒绝/重复反馈，快照完全不变 |
| rules | 未知实体、额外字段、非法类型/效果、信任越界 | validation/规则失败，无部分状态修改 |
| rules | 主动事件一次性与兄弟分支隔离 | 不重复奖励/事件，不修改父或兄弟快照 |
| rules | 证据互锁、结局不可达、搜索上限 | 校验不通过；超限为 inconclusive，不能冒充通过 |
| rules | 玩家公开投影 | 未知证据、隐藏真相、角色秘密不泄露 |
| legacy | 原有 Demo 三结局和已保存节点回放 | 新旧版本分派正确，旧内容原样且无生成调用 |

规则与兼容套件全部通过才满足对应机器验收；用户审定是另一个门槛。动作数和已访问地点计入报告，不从动作数推算游玩分钟数。阶段 1 可用错误 JSON 模拟结构入口，不能据此宣称真实模型或重试执行器已验收。

## 4. 后续故障与模型案例

阶段 2 必须新增注册表/执行器模拟案例：未知工具、参数错误、handler 失败、永久错误不重试、安全瞬态故障后成功、重试耗尽、单次/总超时、格式错误、修复失败、预算不足、Trace/usage 写失败、幂等和失败后恢复；检查实际 attempt 数、无非法节点、父状态不变及轨迹完整。

阶段 3 增加图片补缺、素材原样复用、并行预算预留和收费不确定；阶段 6 增加并行生成、审核误报、一次修复与截止时间共享。真实模型案例记录故事、父状态、行动、模型、上下文和 prompt 版本，以及开始/结束时间、usage、价格版本及结果；未配置密钥或供应商调用失败的任务如实计入失败，不能回退 Demo 后算成功。

## 5. 输出与可复现性

fixture 比对使用 UTF-8 文本的 LF 规范化字节 SHA-256（fixture_hash_mode=utf8-lf），同时记录原文件 fixture_raw_sha256；Windows Git 换行转换不改变固定案例身份，正文及其他字节变化仍拒绝。每次报告包含 run ID、时间、Git commit、评测口径版本、suite、case manifest/fixture SHA-256、模型/引擎/prompt 版本（无模型时明确 none）、总数及各终态、成功率、逐案失败详情和执行时长。模拟测试记录故障种子/时钟设置；真实调用另报时延、fallback、token 和估算费用，缺 usage 的项目标未确认。

stdout 给出摘要；结构化 JSON 保存逐案状态和结果引用，后续报告引用同一 run ID，不手工改失败记录。集成测试缺测试库时标记未执行并返回非零验收结果；纯规则套件仍可单独运行。密钥、连接 URL、会话令牌不进入输出，内部真相与候选稿只保存在本地受控产物，不进入公开评测展示。

阶段 5 在此基础上形成完整普通流水线报告；阶段 6 至少 30 组配对案例和一位评审的评测仍按原计划执行，不能用阶段 1 的规则成功率替代。
